### What the wrapper emits on allow

On an allow the wrapper prints the literal line `{}` (exit 0), for both protect-bash and protect-files (observed directly, e.g. `git status`, `Write` to a path outside the install). The `ls` in item 4 produced `{}` from protect-bash and then executed normally under `--permission-mode default`, so Claude Code 2.1.x treats `{}` as a no-opinion allow. (The corpus recorder's classifier also reads empty output as allow; both shapes are accepted there.) backup-before-edit and snapshot-before-tool print nothing on stdout.

## Latency (M4) -- wrapper fork removal, 2026-10-02

**Gate: still FAILS on this machine under load** (worst p95 > 1000 ms). The wrappers' own forks are gone;
what remains is CPU contention, the interpreter start, and (for session-kb-guard) `tools/kb-guard.sh`.

Change: the five Claude wrappers locate their install with builtins only (parameter expansion instead of
`dirname`, `cd` in the wrapper's own shell instead of three `$(cd ... && pwd)` subshells, `/c/x` -> `C:/x`
converted textually with `pwd -W` kept only for MSYS mounts such as `/tmp`), stamp with `printf '%(...)T'`
instead of `date`, and `mkdir -p` only when the heartbeat directory is missing. Forks left on the hot path:
`$(cat)`, the `$(... | python)` engine call. setup.sh now writes a regular Python over the Microsoft Store alias
when both exist (this machine: Python310 over the 3.12 alias).

Context: MEASURED CPU load 20-79 % (Win32_Processor LoadPercentage) throughout -- 5 `claude`, 10 `node`,
14 `python` processes from other sessions on a 28-thread machine. Every number below is under that load,
not idle; tails (p95) are dominated by it.
