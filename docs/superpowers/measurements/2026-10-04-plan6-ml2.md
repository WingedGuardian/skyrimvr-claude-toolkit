### Table A — mechanism (decided in Task 5 from Tasks 1–3)

Rows are probe ids from Tasks 1–3.

- **MIN-BAR**: P1 `>`, P3 `cp`, P9 `Set-Content`, P19 python `open('wb')`, P22 `shutil.copyfile`, P29
  Codex `apply_patch` Update, P30 Claude `Write`. These are the accident shapes that actually happened
  (L3: all 4 X4 incidents were in this set).
- **REQUIRED**: every overwrite row P1–P33.
- **COMPAT**: C1–C10. **READS**: R1–R3. **UNLOCK**: U1–U5.

| Outcome for a mechanism | Verdict for that mechanism |
|---|---|
| Any READS row fails | ineligible |
| Any UNLOCK row fails, including Python-free, manifest-missing, or ≥ 1 residual deny ACE | ineligible |
| Any COMPAT row fails that is a **routine** operation: C1 xEdit/xelib load, C2 save own plugin, C5 Vortex deploy/purge/collision, C6 MO2 VFS | ineligible |
| A COMPAT row fails that is a **deliberate master edit** (C3 is *supposed* to fail; C4 clean-after-unlock must pass) | C4 failing → ineligible |
| Apply + remove over the full VR target set > 2 s total (needed for session-start relock) | ineligible |
| Eligible but misses any MIN-BAR row | ineligible (a lock that misses the common accidents is false assurance) |

**Choice:** among the eligible mechanisms, take the one that blocks the most REQUIRED rows. On a tie,
the one with fewer parts wins (M-A before M-B before M-C before M-D). **No eligible mechanism → no lock
(D5 option B):** Layer 2 is recovery only, Tasks 8–11's lock parts are skipped (state, shadow mode,
`skydoctor`, self-protection and recovery still ship), and `skyguard lock` prints
`not available: M-L2 failed (<row>)`. The deletion rows D1–D7 are recorded but **never decisive**: a
deleted master is loud, since the game won't start and Steam verify restores it, while an overwritten
one is silent.

Notes per row (MEASURED, from the recorded stderr and post-state):

- **Rename-over** (P8 `mv`, P24 `os.replace`, P33b `renameSync`, P16 `Move-Item -Force`) and
  **unlink-then-create** (P4 `cp -f`, P7 `sed -i`) need DELETE on the target, which no mechanism
  denies. They are stopped only where the read-only bit stops them and the actor cannot clear it.
  Under M-B (no bit) P24/P33b replace the file; under M-A/M-C, MSYS `mv`/`cp -f`/`sed -i` and
  PowerShell `Move-Item -Force` clear the bit themselves (`WA` allowed) and succeed. Under M-D the
  `WA` deny stops the bit being cleared: `cp: cannot remove …: Permission denied`,
  `Move-Item: Cannot create a file when that file already exists`.
- **`-Force`** (P10, P12, P15 — `Set-Content/Out-File/Copy-Item -Force`): open under M-A (the
  cmdlet clears the bit), blocked under M-B/M-C/M-D (the `WD` deny holds whatever the bit is).
- A replaced file is a **new file object with no lock** (post-state: bit and/or ACE gone). E.g. M-A
  P7 `sed -i` left a read-only new file (MSYS copies the mode) but different bytes.
- **D7 rename-away** (`mv f f.bak`) is open under every mechanism: renaming the file needs only
  DELETE on it. The locked object then lives on as `f.bak`; the vanilla name is free to be
  re-created. Recorded, never decisive (Table A).
- **T1 `os.utime`**: open under M-A/M-B/M-C (it needs `FILE_WRITE_ATTRIBUTES` only), blocked by M-D's
  `WA` deny. Tools that stamp times on a vanilla master will fail under M-D — checked in Task 3.
- **Reads** R1 (python), R2 (pwsh 7 `-AsByteStream`, PS 5.1 `-Encoding Byte`), R3 (1 MiB `mmap`),
  T2 (attribute read): all OK under all four mechanisms.
- **WSL rows**: UNMEASURED (L12: only `docker-desktop`; no distro installed, none will be).

**Comparison with X4 (L3: read-only attribute blocks 11/14; not `rm -f`, `Remove-Item -Force`,
`Copy-Item -Force`):** M-A here agrees on all three named misses (D1 open, D2 open, P15 open). It
differs in scope, not in direction: this matrix has 38 write rows, and M-A misses 11 of them,
including four the X4 list did not have (`cp -f`, `sed -i`, `mv` over, `Move-Item -Force`) and
`Set-Content/Out-File -Force`. No disagreement on any row both measured.
